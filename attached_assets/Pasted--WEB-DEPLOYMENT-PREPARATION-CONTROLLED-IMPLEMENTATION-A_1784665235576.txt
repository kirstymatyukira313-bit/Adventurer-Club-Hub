# WEB DEPLOYMENT PREPARATION — CONTROLLED IMPLEMENTATION

Act as a senior software engineer with extensive experience in Expo SDK 54, Expo Router, React Native Web, Metro, TypeScript, and production deployment.

The existing Adventurer Club Hub application is currently a functioning Expo application with:

- Expo SDK ~54
- Expo Router ~6
- React Native
- React Native Web installed
- React DOM installed
- Metro bundler
- TypeScript
- AsyncStorage for local persistence
- Existing native Expo Go deployment workflow

The application currently runs successfully as a mobile/Expo application.

The goal is to add a proper browser-based web build pipeline so the app can eventually be hosted as a live web application.

This is a controlled infrastructure and compatibility task.

DO NOT redesign the application.

DO NOT modify the existing visual design.

DO NOT modify existing user flows unless required for web compatibility.

DO NOT modify the data model.

DO NOT migrate AsyncStorage to a database.

DO NOT change the storage key:

"adventurer_club_state_v1"

Existing user data persistence must remain compatible.

==================================================
PHASE 1 — PRESERVE THE EXISTING APP
==================================================

Before making changes:

1. Inspect the existing project structure.
2. Confirm the current native/Expo Go build workflow.
3. Confirm the current package scripts.
4. Confirm the current AsyncStorage implementation.
5. Confirm the current Expo Router configuration.

Do not remove the existing native build process.

The existing build script must continue to work.

==================================================
PHASE 2 — ADD A SEPARATE WEB BUILD PIPELINE
==================================================

Add a separate browser build command.

Do not replace the existing native build script.

Create a separate web build process equivalent to:

expo export --platform web

The web build must produce an actual browser-loadable static application.

The output must not be:

- an Expo Go QR landing page
- a native OTA manifest server
- a mobile-only bundle

The output must be a real web application that can be served by a standard static hosting platform.

Add a separate script if appropriate, such as:

web:build

Do not remove or break the existing:

build

serve

dev

typecheck

scripts.

==================================================

Audit all platform-specific packages and usages.

Focus specifically on:

- expo-notifications
- expo-glass-effect
- expo-haptics
- expo-blur

Do not modify packages unnecessarily.

Only make changes required for reliable browser execution.

==================================================
PHASE 4 — EXPO NOTIFICATIONS
==================================================

expo-notifications does not support browser execution.

Prevent native notification code from executing on web.

Any code involving:

- notification handlers
- Android notification channels
- notification permissions
- notification scheduling

must be protected by platform-aware logic.

Native behavior must remain unchanged.

On web:

- the application must not crash
- unsupported native APIs must not execute
- existing reminder functionality should degrade gracefully

Do not delete reminder functionality.

If necessary, display an appropriate web-compatible fallback state.

Determine whether the package has reliable web support.

If it does not:

- preserve the existing native implementation
- provide a safe web fallback
- do not redesign the component
- preserve the existing visual hierarchy as closely as possible

Do not remove visual elements unnecessarily.
